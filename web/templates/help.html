⚡ What is Energy Meter Tracker?
⚠️ Informational use only. Energy Meter Tracker provides a close approximation of your consumption based on local sensor readings. It cannot replicate your supplier's authoritative meter reconciliation. Do not use this data for billing disputes or formal energy accounting.

Required Hardware — The addon is intended to be used with an IHD/CAD capable of providing meter readings at reliable regular intervals (0.1Hz).

Energy Meter Tracker is a Home Assistant add-on that records your electricity usage in configurable reconciliation periods — matching the intervals used by your energy supplier for billing. It stores meter readings at each boundary so you can see exactly what happened in any given period, including how much of your usage was from the grid versus your battery, EV or other device.

🕐 Meter Reconciliation Period

Each block covers exactly one reconciliation period: for example 09:00 → 09:30 at 30 minutes, or 09:00 → 09:05 at 5 minutes. In the UK, energy suppliers use 30-minute half-hourly (HH) settlement periods. Configure the reconciliation period to match your supplier before data collection begins. It cannot be changed without clearing all historical data.

Why interpolation matters: If your meter reads 1000.0 kWh at 09:28 and 1000.5 kWh at 09:32, the engine calculates that approximately 0.25 kWh crossed the 09:30 boundary — not 0.0 kWh (last reading before) or 0.5 kWh (total since last reading).
⚖️ Main Meter & Devices

The main meter reads directly from your smart meter via a Consumer Access Device (CAD) and is the authoritative source of truth for how much energy crossed the grid boundary.

Devices let you track individual loads — a home battery, EV charger, or heat pump. Each device has a Meter Type which enables additional configuration and drives the Live Power page display:

  • 🔋 Battery — enables SoC sensor and inverter power sensor fields. Shows a battery icon with charge level and an inverter gauge on Live Power.
  • 🚗 EV Charger — enables a charger power sensor field. Shows a unidirectional charge gauge on Live Power. Mark as V2X capable if the vehicle supports vehicle-to-grid.
  • ♨️ Heat Pump — enables a heat pump power sensor field. Shows a unidirectional power gauge on Live Power.
Direct import
In each block, device consumption is subtracted from the main meter's total import. Whatever is left is direct import — the portion of grid import not accounted for by any device. This is what's used for billing calculations.
Inverter possible
Devices marked inverter possible may show consumption from battery discharge rather than grid. The engine allocates grid energy to protected loads first, then to inverter devices. This flag is set automatically for Battery type meters and can be enabled manually for any device (e.g. an EV fed by a battery inverter).
⚠️ Per-device export tracking and solar generation are not yet supported. Individual device export (e.g. battery discharging to grid, V2G from a V2X-capable EV) is not yet broken down by device. Solar generation tracking is planned for a future release.
⚙️ Meter Configuration

Meter IDs are assigned automatically and not shown in the UI — the Device Name (for devices) and Site Name (for the main meter) are the user-facing identifiers used throughout charts and reports. Names must be unique, 40 characters or fewer, and contain only letters, numbers, spaces and ' - & ( ) .

Deleting a device permanently removes all associated historical data from the database. There is no recovery path — ensure you have a backup before deleting.

The change reason prompt only appears when billing-significant fields change (billing day, block period, timezone, currency). Routine sensor or name updates save immediately.

Battery sensors

  • Read sensor — cumulative kWh consumed (required)
  • SoC sensor — battery state of charge in % (optional, Live Power only)
  • Inverter power sensor — live inverter power in W or kW (optional, Live Power only)

EV / Heat Pump sensors

  • Read sensor — cumulative kWh consumed (required)
  • Charger / Heat Pump power sensor — live power in W or kW (optional, Live Power only)
ⓘ The SoC, inverter power, charger power and heat pump power sensors are informational only — they are displayed on the Live Power page but are not recorded in blocks or used in any billing calculations.
📡 Sensor Requirements

Main meter — Read sensors

  • Must be cumulative kWh — ever-increasing total, never resets
  • High-frequency updates preferred (10–60s) for better boundary interpolation
  • Typically from your CAD via MQTT integration
  • Example: sensor.smart_meter_electricity_import

Rate sensors

  • Must be the current rate per kWh — the live tariff rate
  • For Agile/flexible tariffs these change each period
  • Example: sensor.octopus_energy_electricity_current_rate

Device — Read sensors

  • Must be cumulative kWh consumed (import only) — not net, not export, not watts
  • Can update less frequently (60s+)
  • CT clamp via PowerCalc, or native device integration (Zappi, Solax, etc.)
  • If no rate sensor is configured the main meter import rate is used

Standing charge sensor

  • Must be a daily standing charge value
  • Can be a fixed input_number helper
  • Only needed on the main import channel
⚡ Live Power Page

The Live Power page shows your current grid power and billing totals. The summary row at the top adapts to your configuration:

  • Live Power gauge — net grid power (negative = exporting). Status pill shows Importing/Exporting/Net Zero with current kW.
  • 🔋 Battery card — appears when a battery device has SoC or inverter power sensors configured. Shows charge level (colour-coded green/amber/red) and a bidirectional inverter gauge (teal = discharging, purple = charging).
  • 🚗 EV Charger card — appears when an EV device has a charger power sensor configured. Shows a unidirectional charge gauge (0 on left, max on right). Gauge scale is derived from the 48-hour history.
  • ♨️ Heat Pump card — appears when a heat pump device has a power sensor configured. Same unidirectional gauge as the EV charger.
  • 🌿 Carbon Intensity card — appears when a postcode prefix is configured. Shows current gCO₂/kWh and 48-hour forecast.
ⓘ Device name detection for Live Power cards uses the Meter Type field set in Meter Config. If no type is set, keywords in the device name or meter ID are used as a fallback (e.g. "battery", "charger", "zappi", "heat pump"). Setting the Meter Type explicitly is recommended.
🔧 Gap Filling

If the add-on is stopped or Home Assistant restarts, the engine detects any missing blocks when it comes back online. It uses the last known reading before the outage and the first reading after to interpolate the missing blocks. Gaps longer than 12 hours are not interpolated — the blocks are left as zero to avoid misleading data.

ⓘ Device gap attribution: The main meter uses boundary interpolation to correctly allocate energy to each block window. Devices use raw cumulative deltas — if no intermediate reads arrived during a gap, the full delta may be attributed to a single block even if it spans multiple windows. This can cause a device to appear to exceed the parent grid import for that block. The engine logs a WARNING and preserves the raw value. This is a known limitation and will be improved in a future release.
🌿 Carbon Intensity

When a postcode prefix is configured (e.g. DE1), the engine fetches half-hourly regional carbon intensity data from the National Grid ESO API. Carbon intensity (gCO₂/kWh) is recorded against each block at the time of finalisation.

  • Forecast vs actual — the API provides a forecast for upcoming slots and actual values ~24 hours later. Both are stored; actual is preferred when available.
  • Generation mix — alongside intensity, the fuel type breakdown (wind, solar, gas, nuclear, biomass, hydro, imports) is stored per block. This data is the foundation for future generation mix features.
  • Historical backfill — on first run with a postcode, the engine backfills up to 60 days of carbon data. Subsequent restarts check only the last 48 hours.
  • Coverage — the Insights page shows the percentage of blocks with carbon data. Blocks from before a postcode was configured will not have carbon data.
ⓘ Only UK postcodes are supported via the National Grid ESO regional API. Enter the outward code only — e.g. DE1 not DE1 3AT. The engine normalises the postcode automatically on save.
📊 Insights

The Insights page provides carbon analysis for any calendar month or year. Use the floating toolbar to switch between Month and Year view, navigate with ← →, and compare against the previous period or same period last year.

  • Carbon Summary — net carbon emitted, your effective intensity vs grid average, export offset.
  • Solar Export — carbon displaced by export, weighted by grid intensity at time of export.
  • Direct Import — grid import attributable to house loads, excluding EV and battery charging.
  • Battery Charging — carbon cost of grid energy used to charge the battery, including AC from grid and usable DC stored (adjusted for round-trip efficiency).
  • EV Charging — carbon cost of EV charging with mileage estimate and petrol comparison.
  • Heat Pump — carbon cost vs equivalent gas boiler.
ⓘ Insights requires carbon intensity data. Blocks without carbon data (predating postcode configuration) are excluded from carbon calculations. The coverage percentage is shown on the Carbon Summary card.
💾 Data Storage & Backup

All data is stored in a single SQLite database:

  • blocks.db — everything: all finalised blocks, config history, meter definitions, and current block state. This is the only file you need to back up.
  • meters_config.json — human-readable config export only. The database is authoritative.

Data is stored in /data/energy_meter_tracker/. After every block finalise, blocks.db is copied to /share/energy_meter_tracker_backup/. A zip snapshot is created automatically before every config save and on demand from the Data Management page.

⚠️ Uninstalling the add-on will wipe /data/. Always ensure you have a recent backup in /share/ before uninstalling.
🐳 Standalone Docker

When running in standalone Docker mode, the add-on connects to your HA instance using a Long-Lived Access Token. The UI is accessible directly at the configured port (default http://<host>:8099). 

panel_iframe:
  energy_meter:
    title: "Energy Meter"
    icon: mdi:speedometer
    url: "http://192.168.1.x:8099"

Embedding charts in Lovelace — use the dedicated Lovelace endpoints: 

http://192.168.1.x:8099/lovelace/billing   # Billing chart
http://192.168.1.x:8099/lovelace/heatmap   # Net energy heatmap
⚠️ The volume mount is essential. Always run with -v /path/to/data:/data/energy_meter_tracker.
🏠 Home Assistant Sensors

After each block finalises, the engine updates four synthetic HA sensors:

  • sensor.energy_meter_import_kwh — total grid import (kWh)
  • sensor.energy_meter_export_kwh — total grid export (kWh)
  • sensor.energy_meter_import_cost — total import cost (£)
  • sensor.energy_meter_export_credit — total export credit (£)

These sensors use state_class: total_increasing and device_class: energy so they are compatible with the HA Energy dashboard and Utility Meter integrations.
