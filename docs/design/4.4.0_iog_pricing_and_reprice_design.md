# 4.4.0 — IOG pricing & the single re-price (first-principles design)

*Merges and supersedes `iog_6hr_cap_design.md` and `iog_cap_device_pricing_design.md`.
This is the build reference for 4.4.0. Where the two source docs and this one disagree,
this one wins; where they still hold (the 4-rate rules, the charged-time cap measure,
the reconciliation algebra) the detail is folded in below and those sections are marked
**(retained)**.*

Status: **design, pre-build.** Nothing here is implemented yet. The goal of the first
build phase is to *confirm this design* end-to-end on the engine / block-store / billing
charts before touching the wider surface area.

---

## 0. Why we are rewriting rather than patching

4.3.2 prices IOG **uncapped** correctly. The 4.4.0 work that was meant to add the
**capped** case — priced segments, an EV/house split, per-device pricing — turned into a
long tail of production patches. Looking back, almost every patch was the same shape:

> an authoritative input changed (a dispatch completed, a block settled, a reconcile ran,
> the VAT calendar changed) and we updated **some** derived fields but not others, so the
> ex-VAT figures, or the EV split, or the segments, or the bands went stale.

The code still carries the evidence: **four independent historical backfill passes**
(`carbon`, `exc`, `iog_split`, `segment`) plus settlement re-runs, reconcile, gap-fill and
import all reaching into pricing separately. Every one of those is a place a derived field
can be left behind.

Two root causes, and the whole 4.4.0 model follows from removing them:

1. **Two competing notions of "the EV"** — the configured physical charger (a real
   sub-meter) and the synthetic dispatch-derived EV — both fed reconciliation and
   presentation, and disagreed. Divergence, stale splits, repair sweeps.
2. **Derived fields maintained piecemeal** — no single operation owned "recompute
   everything this block derives," so each trigger patched its own subset.

4.4.0 is not a teardown of the storage. It is a **restart of the reconciliation inputs and
the presentation layer** around two invariants:

- **One EV/device source, selected by account type.**
- **One atomic re-price: all derived fields, recomputed together, on every trigger.**

---

## 1. First principles (the axioms everything else derives from)

**Principle 0 — the design *is* the model, and every code path is confined to it.** There is
one pricing model. Features (import, backfill, settlement, reconcile, delete, charts, usage
stats, carbon) *conform* to it; none re-implements pricing or carries its own near-duplicate
variant. This is the explicit anti-goal of 4.3.0/4.3.1/4.3.2, where monolithic paths did
virtually identical things slightly differently, so every minor requirement became an epic
testing effort and a fresh source of drift. If a new requirement can't be expressed by
extending the model (a new device label, a new resolver, a new emitted field), that is a
signal to change the *model*, deliberately and in one place — never to bolt a parallel path
onto a component. The whole point of 4.4.0 is that small changes stay small.

1. **The settled block is the only truth.** Octopus/DCC gives us, per half-hour, a total
   grid-import **kWh** and **cost** — nothing else. That pair is authoritative for both
   axes and is never recomputed or overwritten by EMT.
2. **Everything else is derived** — rate, ex-VAT rate/cost, the house/EV(/device) split,
   segments, band labels, the cap boundary — and is a pure, deterministic function of the
   authoritative inputs. Derived data is disposable: it can always be rebuilt from truth.
3. **EMT's value-add is the split Octopus won't itemise.** Octopus computes a house-vs-EV
   split once the 6-hour cap engages but only shows it *aggregated*, and abandons the PDF
   bill under cap because it's hard to present. EMT splits **every** block — including the
   transition block — and reconciles it back to the settled total. The split is a derived
   presentation/insight layer; it never rewrites the total.
4. **Truth flows down, never up.** The split reconciles *into* the settled cost. If the two
   tariff rates leave a residual at a boundary block, the settled total wins and the
   residual is absorbed. We never let a derived estimate revise the settled figure.
5. **Account type is the top-level key.** non-IOG / IOG-uncapped / IOG-capped is decided by
   the config period's tariff code (one source of truth, no manual toggle). The *same* data
   model serves all three; the cap is simply engaged or not.
6. **Presentation only plots.** Charts, usage stats and the billing breakdown read
   already-correct derived values and draw them. They never re-derive tariff rules, read
   band labels, reconstruct "which rate applies," or recompute a split.

## 2. Authoritative vs derived — the ledger

The single most useful thing this doc can pin down is *which columns are facts and which
are recomputable*, because "is this stale?" then has exactly one answer: derived data is
never stale because it is only ever written by the re-price function.

**Authoritative (facts — never recomputed, never hand-edited):**

- Per block: settled grid-import **kWh**, settled **cost**, settlement state.
- Raw dispatch history (`completed` windows: `raw_start`, `raw_end`, delivered kWh).
- Raw meter reads / imported HH values (import + export).
- The tariff/VAT schedule effective by date (unit rates, standing charge, VAT calendar,
  `ev_device_off_peak` / `ev_device_peak` schedules, off-peak window).
- Account/config: tariff code (→ account type), configured devices.

**Derived (a pure function of the above — only ever written by the re-price):**

- `rate` (= cost ÷ kWh), `rate_exc` / `cost_exc` (VAT), effective p/kWh.
- The house/EV(/device) split: per-device kWh, cost, rate.
- Segments (§5) and their reconciliation.
- Band **labels** (off_peak / peak / day) — a *name for a rate*, computed at emit time,
  **not stored as an independent fact** (§5).
- Cap state: cap-day charged-time used, boundary slot + fraction, over/under.
- **Energy substrate for both axes:** per device, **both** the grid-clipped kWh (billing
  basis) **and** the unclipped kWh (full draw), plus house generation. Billing consumes the
  clipped figure; carbon consumes the unclipped one (§3a). Carbon (kWh × CO₂ intensity −
  generation offset) is its own derived axis — price never enters it.

> **Schema guidance:** keep the authoritative columns as they are; move or clearly
> namespace the derived columns so a reader can tell facts from computed values at a
> glance. Physically separating them (a derived-values view/table, or a `d_` prefix) makes
> the invariant self-documenting. **Retain** the physical EV device's raw data — it is the
> non-IOG fallback (§3) and may matter for future device tariffs — it is just never a
> reconciliation input on IOG.

## 3. The device/EV source — selected by account type

The crux fix. There is exactly **one** EV quantity per block, chosen by account type; the
two sources are never blended.

| Account type | EV source (billing basis) | Cap / 4-rate | Physical charger |
|---|---|---|---|
| **IOG, dispatches present** | **synthetic dispatch EV**, grid-clipped (`EV = min(completed-dispatch Δ, grid import)`) — literally what Octopus bills and what counts toward the cap | engaged (capped) or off (uncapped) | retained, *indicative only*, never in the split |
| **EV but not IOG** (no dispatches) | **physical EV device**, already grid-clipped to measured CAD import (4.3.2) — "how much grid went to the car" | none (single/Agile rate) | **is** the source |
| **No EV** | — | none | — |

Both sources are clipped at the **grid-import boundary**, so solar/battery never inflate
either — on IOG they should nearly agree anyway; the divergence we chased came from *using
both at once* and from stamping the dispatch split once without re-attributing
late-completing dispatches. One source, selected by type, removes that class of bug.

**Generalise the selector into a per-device attribution resolver.** Today it only needs to
answer "EV = dispatch (IOG) or physical device (non-IOG)." Shape it so that adding
"battery = X signal" or "heat pump = Y signal" later is a *new resolver*, not a
restructure — see §8 on why this matters. Build only the EV resolver now; do **not**
hard-code the assumption that there is exactly one device.

### The 4-rate rules **(retained from `iog_6hr_cap_design.md`)**

Two rates exist: off-peak and peak. Per half-hour:

1. **Home off-peak (guaranteed):** inside the agreement's off-peak window (read from the
   schedule, 23:30–05:30 today) the house is always off-peak, cap-independent.
2. **Car allowance:** the car gets up to **6 hours of actual charging** per cap-day
   (noon→noon local) whenever Octopus dispatches it.
3. **Home freebie:** when the car is dispatched **outside** the window, the house also gets
   off-peak — **only while within the 6-hour allowance**.
4. **Standard / EV-peak:** outside its window the house default is the day rate; once the
   car passes 6 h (or Boost/Bump) the car flips to `ev_device_peak`, and the rule-3 freebie
   is withdrawn on over-cap out-of-window slots (house → day). **Bump/Boost charging is
   peak even within the cap.**

Boundary consequences: in-window over-cap → car peak, **house stays off-peak** (the only
"house off-peak while car peak" case); out-of-window over-cap → both at peak/day.

### The cap measure — charged time **(retained)**

The cap is **6 hours of actual charging** per cap-day, not dispatch wall-clock. *(The
6-hour length is **configurable** — `iog_cap.CAP_HOURS`, env `IOG_CAP_HOURS`, default 6.0,
resolved at call time so a runtime change takes effect — used to exercise the cap path on a
3-hour fixture ahead of a real capped account, and a hedge should Octopus change the cap.)* A slot's
charged time = `|delivered kWh| ÷ charge_power`, `charge_power = 2 × the cap-day's fullest
delivered half-hour` (the charge-card method). Cumulative charged time is summed in time
order; the **boundary** is the slot where it first reaches 6 h, and that slot's within-cap
fraction = `(cap − cumulative_before) ÷ slot_charge_hours`, so the boundary block bills as
a blend. The transition rate itself may never be published in the API — **we never read it;
we derive the boundary and let the settled cost close the books.**

**Decided positions (were "unknowns"; now locked — settled cost makes them non-blocking):**

- **The transition block is real and Octopus costs it.** Mid-block rate changes are a
  first-class case under the cap, not an edge case — Octopus costs the *actual* charged-time
  transition, it does **not** assume a clean "after 12 half-hour blocks." That block **will
  hold a cost** (it may or may not expose a rate); the cost is authoritative and we split it
  ourselves. We locate the mid-block boundary with the **charge-card elapsed-charging-time**
  calculation (already built), price the off-peak and peak portions, and reconcile to the
  settled cost. We never need Octopus's boundary *rate* — only their cost.
- **House is peak during peak times once the cap is engaged.** Octopus never explicitly says
  the freebie survives over-cap out-of-window charging; the only coherent reading of the
  4-rate rule ("while within your car allowance") is that it does not — so after the cap
  engages, house out-of-window reverts to the day rate. **Adopted as the design.** Still
  empirically confirmable on the first real over-cap daytime slot, but it cannot produce a
  wrong bill (settled cost overrides), so it is not a design open.

### The boundary block bills to TWO real rates, not a blended average — why the summary stays tidy

The cap crosses mid-block (6 h of *elapsed charging*, so almost never on a slot edge), so the
boundary block's kWh is **split**: the within-cap kWh at off-peak, the over-cap kWh at peak.
The billing summary distributes those two slices into the two **real** rate rows — it never
carries the block's blended average *as a rate*. This is the reason the pre-segment
"transition row" was retired, and it matters at scale:

- Every over-cap day's boundary block blends at a *slightly different* rate (the cap lands at a
  different point each day). A blended-transition-row approach would therefore sprinkle a month
  with **dozens of near-unique average rates** — one per over-cap day.
- Distributing the boundary kWh to its two **constituent** rates instead collapses a whole
  month of over-cap days back to the clean bands: EV off-peak / EV peak / Home off-peak /
  Home day. Tidy and true.
- The two rows for a band read **one shared per-band rate** (kWh-weighted over EV+Home for that
  band), so EV and Home never disagree within a band from independent per-block cost-rounding,
  and a genuine in-period rate change (> `_SPLIT_BAND_EPS`) forms its own band at its own rate —
  rate-change-safe. The bill-method breakdown collapses the same way.

The block's chart rate **line** still shows its genuine blended figure for that half-hour
(faithful under the hood); only the summary *attribution* is per-constituent. So "no transition
row" is a **feature** of segmentation, not a gap.

### Reconciliation invariants **(retained from `iog_cap_device_pricing_design.md`)**

On **every** block, capped or uncapped: `Σ device kWh == grid kWh` and
`Σ device cost == grid cost`. The algebra closes only because the priced EV slice equals the
**dispatch** EV (not a physical charger's metered kWh):

```
Σcost == grid_cost  ⟺  (D_ev − imp_kwh_ev)·(ev_rate − house_rate) == 0
```

i.e. it reconciles when `D_ev == imp_kwh_ev` (or uncapped, where the two rates are equal).
The house slice is the reconciling plug on both axes. This is why the **synthetic** EV, not
the physical one, drives the split.

### 3a. Billing wants clipped EV; carbon wants *unclipped* EV

Billing and carbon need **different EV quantities from the same dispatch**:

- **Billing EV = grid-clipped** (`min(dispatch Δ, grid import)`) — only the metered portion,
  because that is all Octopus charges for. This is the split basis above.
- **Carbon EV = unclipped** — the car's **full** draw. When a smart charge pulls more than
  the grid supplied in a slot, the difference came from **behind the meter** (house battery /
  solar-direct / self-consumption) and never crossed the grid meter.

The **credit is the draw gap, not an export offset.** Export/outgoing figures do NOT enter it
(the dev DB only gets an export figure at settlement; Highgrove has the export MPAN — neither
touches this). Valued at the *current* grid intensity, the behind-meter energy is avoided grid
carbon:

    unclipped = the car's FULL draw for the slot (completed dispatch)
    clipped   = min(unclipped, grid import)   — what the grid actually supplied (billing basis)
    behind    = unclipped − clipped           — behind-meter, zero grid carbon

    grid_g   = clipped   × intensity   — the EV's ACTUAL grid carbon
    saving_g = behind    × intensity   — avoided grid carbon (the credit)
    gross_g  = unclipped × intensity   — grid_g + saving_g (the 4.3.2 sub-meter gross figure)

4.3.2 already does exactly this with the physical Zappi (PASS 2 splits a device draw into
`kwh_grid` clipped + `kwh_battery` self-consumption; the credit falls out as device-gross
minus grid). 4.4.0 keeps the **identical methodology** but re-sources the EV from the
**synthetic dispatch device**, since on IOG there is no physical meter. **Single-source rule**
(mirrors cost): on IOG the synthetic dispatch device IS the EV carbon source; any configured
physical device is ignored for the EV carbon axis. Carbon is a **separate derived axis** —
price never enters — recomputed wholesale from its inputs (unclipped + clipped EV energies,
house grid energy, CO₂ intensity), never patched piecemeal. Δ5 ships the pure core
(`carbon.py`); Δ5-wire feeds the **Insights** Carbon Summary via `carbon.period_ev_saving`.

**Two surfaces, and the guard.** Carbon shows in two places — the net heatmap and the Insights
Carbon Summary — each independently reading stored `carbon_g` (the duplication is legacy debt to
retire onto the one emit). Because the EV source moves physical→synthetic, **byte-identity is not
the guard on the EV axis**: on an IOG account with a physical charger the number changes by design
(it reconciles to Octopus's completed dispatch, not the old device meter). The guard is
byte-identical on non-IOG and on main-meter carbon everywhere; the IOG EV figure is validated
against dispatch. Δ5-wire adds Insights' `ev_carbon` as an **additive** field (all existing fields
byte-identical); the heatmap and single-source *display* preference are Δ5b.

**Historical exc must use the full agreement history (P3.3a-fix).** Re-pricing history through the
*current* live schedule is wrong — it can't price blocks under prior tariff agreements. The exc
axis must scale the block's stored inc rate by the tariff exc/inc ratio over the FULL agreement
segments (`_exc_rate_for_block` + `_build_channel_rate_segs`), and is **gated to imported / DCC-
settled** blocks: provisional live blocks intentionally carry no stored exc (the view falls back to
inc÷1.05) until settlement stamps it, so the sweep must not fill them. Conformance separates
**regressions** (a changed/lost stored value — the real signal) from **fills** (adding exc where a
settled block legitimately lacked it).

**Structural safety of the sweep (why P3.3c is safe).** The split and exc column writers
(`set_blocks_iog_split`, `set_blocks_exc`) are **fill-null-only** (their SQL only touches rows
whose target column IS NULL), and `set_blocks_exc` additionally carries the imported/settled
coverage gate in SQL. The sweep also only ever processes blocks that are MISSING segments. So the
sweep can only ever *add* a derived value to a block that lacked one — it can never overwrite or
change a value the backfills (or the forward path) already wrote. Retiring the legacy backfills in
favour of the sweep therefore cannot cause a data regression; the conformance harness proves the
sweep's *derivation* matches (so fills are correct), and the fill-null-only writers guarantee the
*persistence* is non-destructive.

### 3b. Rate is FINALISE-TIME; reprice INHERITS the overlay, never re-derives it

The off-peak-vs-peak decision is made at **finalise** — base schedule + the smart-charge
overlay, gated on a *started* smart-charge captured while planned — and stored on the block.
`reprice` **inherits** that decision as an input; it must never recompute the overlay from
dispatch-slot capture (a blind recompute would silently degrade a correct off-peak to peak).
Under the cap, `reprice`'s only new job is to **segment the already-finalised rate**: split
EV/house, and flip the **over-cap portion of SMART charging** to EV-peak (withdrawing the
house freebie there). It never re-qualifies smart-vs-bump or in/out-window.

- **Cap allowance = smart charged-time only.** A bump/boost is peak by finalise and never
  consumes the 6-hour allowance — a user who bumps pays peak and must not also lose
  allowance ("pay twice").
- **Adjust as new information arrives — this IS the atomic re-price, not the forbidden
  recompute.** A block finalises on whatever exists then (planned/started, or nothing),
  flagged provisional; a completed dispatch lands hours later → re-price; DCC settles ~2 days
  on → re-price to authoritative. Each is the one re-price firing on a new authoritative
  input. What is forbidden is re-deriving the overlay for a block whose signal has aged out
  and no new information exists.
- **Confidence flag (the user-facing promise) — already built.** The `needs_review` /
  `review_reason` columns are the confidence marker ("we weren't fully confident in the price
  for this block"). They are set by `_reconcile_decision(has_started, has_completed,
  has_planned, …)`, which already encodes §3c: `has_started`→off-peak; not `has_completed`→peak
  (revert); completed-but-negligible→peak; completed-not-started-with-planned→**`review`, left
  at peak** (ambiguous bump vs paused); completed-only→promote off-peak (`rate_reconciled`).
  `reprice` consumes this decision; it does not reinvent it. This is EMT's edge: a predicted
  price ~2 days before Octopus settles, honest about its certainty.

### 3c. Settlement CAN revert off-peak → peak (arbitrated — supersedes intelligent_rates_design)

The two source docs disagreed; resolved here. Octopus routinely schedules a tiny dispatch
and then does **not** stamp it completed, billing that slot at peak. So:

- **0 delivered** in a provisionally-off-peak planned slot → it never charged → peak (no EV
  contribution either way).
- **Minor delivery but no completed dispatch signal** → **revert to peak** (EV and house).
  The flagged blocks (12/08 20:30, 13/08 21:00, 14/08 20:30, 16/08 13:00–13:30) are exactly
  this pattern.

This is the shipped `_reconcile_decision` (§3b), so §3c is documentation of existing
behaviour, not a change. If Octopus changes this behaviour the model self-corrects — the **DCC
settled cost/rate is always the final authority**.

> **Verified safe (was flagged open):** the `completed-only → promote off-peak` branch is
> already gated by the **negligible-energy guard** (`mag < small_kwh → peak`), which runs
> *before* it. So Octopus's tiny scheduled-but-never-completed overrun prices peak — either via
> "not has_completed → peak" (no complete stamp) or "completed-but-negligible → peak". The
> promote fires only for a MATERIAL completed dispatch with no captured plan (the legitimate
> offline / re-import case). Confirmed against the flagged blocks; the rare miss self-corrects
> at reconcile.

### 3d. Keep the dispatch history — do not prune; stamp eligibility

The old "non-reconstructable / never blanket-recompute" standing principle (intelligent_rates)
was a workaround for pruning the smart-charge signal at 90 days. **Decision: retain the
dispatch history rather than prune it** — Octopus persists completed dispatches, and now that
we use the lifecycle it is valuable (bug diagnosis; re-price reading real signals). Combined
with **stamping the finalise-time eligibility as a durable derived fact** on the block
(off-peak-eligible + why: started-smart / completed-only-promoted / bump), re-price reads a
stored fact instead of dead slots, so recompute is **safe** — which is what lets the
one-re-price model and the migration run without degrading history. Blocks predating the stamp
keep their finalised rate (nothing to reconstruct → don't try). The standing principle is thus
rewritten: *re-price reads stamped eligibility; it never re-derives the overlay from slot
capture.*

### 3e. Rate/cost source by account type — including non-API / own-cost-sensor users

The account-type key (non-IOG / IOG-uncapped / IOG-capped) is about the EV/cap layer.
*Orthogonal* to it is where a block's **rate and cost** come from — and the segment model is
agnostic to that, which is exactly why non-API and cost-sensor users fall out cleanly instead
of fighting the machinery.

| Rate/cost source | How the block is priced | In the segment world |
|---|---|---|
| **Schedule / IOG (API)** | rate self-derived (schedule base + dispatch overlay); settled DCC cost authoritative, re-materialised at settlement | full EV/house split + cap bands + boundary blocks |
| **Measured cost / own cost sensor** (`meas_cost` via Measurements `cost_incl`, or `sensor.energy_meter_import_cost`) | the measured **cost** is authoritative → effective rate = `cost ÷ kWh`; the user's own per-slot algorithm (tiers, standing, wholesale-tracking) is preserved **to the penny** | a **single house segment** reconciling exactly to that cost; PASS 2 attributes devices at the effective rate; the IOG overlay/split/cap layer is **inert** (no schedule/dispatch → no-op, never touches the cost) |

Key distinction (from `intelligent_rates` §1c): EMT never lets a sensor dictate the
**rate-overlay** decision (it self-derives the off-peak overlay), but a measured **cost** IS
authoritative — same family as "settled DCC cost is authoritative." So a user varying their
cost by their own algorithm is honoured; the only thing they don't get is a 4-rate/cap
breakdown, which is correct because they don't have that tariff. None of the cap/dispatch
machinery is redundant-in-their-way — it is **dormant**, and the cost/segment/device model
carries their own numbers faithfully.

### 3f. Bands stay — derived at pricing, not retired at render (closes the "#1" question)

Bands are **kept**, not retired. The design principle "a band is a label derived from the
rate" is **already satisfied** by deriving it *at pricing* from the rate + the agreement's
tariff (the source of truth), and storing it consistently — the atomic re-price keeps band
and rate in lock-step (verified: 0 segments where the band disagrees with the rate). Reading
the stored segment band is therefore reading the tariff-derived classification; re-deriving it
at *render* would need the tariff plumbed into the chart to reproduce the same value —
redundant, and off-model (we don't re-derive `rate_ev`/`cost_ev`/segments at render either).
The only genuinely-stale mechanism — the old block band **columns** — is already bypassed
(readers use the rate), so those columns are **vestigial: deprecate-in-place, never dropped**
(keep-don't-prune, §7a). Net: nothing is retired.

### 3g. The hybrid seam — recorded physical pre-seam, synthetic post-seam, one continuous EV

§3's selector ("synthetic on IOG, physical otherwise") is refined by a **seam** in time: the
point an account's history becomes dispatch-authoritative. Octopus exposes only ~90 days of
completed dispatches, and only forward from when EMT began recording them, so a long history has
**no dispatch** before that seam. The per-block rule:

- **Post-seam** — a completed dispatch exists (`imp_kwh_ev IS NOT NULL`): the synthetic dispatch
  EV is authoritative and **supersedes** the physical charger (per §3).
- **Pre-seam** — no dispatch: the **recorded physical** EV device stands. It is the only EV
  signal there and is already grid-clipped (4.3.2).

`_hybrid_ev_by_block` is the one resolver every surface reads (`imp_kwh_ev IS NOT NULL` →
synthetic, else recorded). The two are presented as **one continuous "EV" identity** — one
colour, one label — so a period straddling the seam reads recorded-then-synthetic with no gap
and no double-count. This is **display/attribution only**: the grid total and the bill are
unchanged (the synthetic-vs-physical difference folds into the house remainder). Additive by
construction — a fully-post-seam range, an uncapped account, or a non-IOG account is
byte-identical.

Why a seam and not "synthetic always": pre-seam we *cannot* reconstruct dispatches (the API's
90-day, `source`-blank limit — the "unbake the cake" problem), so the recorded physical EV is
the best available truth there; discarding it would blank the EV split for all pre-seam history.
Post-seam the synthetic is authoritative (it is what Octopus bills). The seam is per-block,
resolved from the data, never a stored date.

**Battery-assist floor.** On a slot where the house **battery** also drew from the grid, the
grid-clipped synthetic EV can still exceed the grid available *to the car* (its own draw plus
the house remainder) — the rest of its charge came from the battery, which dispatch cannot see.
Folding that excess out of the house would render a spurious **negative Direct** bar, so the fold
caps the EV to the grid available and floors the house at 0 in **both kWh and cost** (the cost
cap moves ALL of the house's held £, not a car-rate-scaled slice, so £ floors with kWh). Slot
total preserved; the bill is untouched (it keeps the battery inside Home and already floors Home
cost).

## 4. The single atomic re-price (the central invariant)

**Re-pricing a block is one deterministic function of its authoritative inputs that
recomputes every derived field together.** Nothing derived is ever written outside it.

```
reprice(block) = f(settled_kwh, settled_cost, raw_dispatch, tariff@date, vat@date, account)
  → rate, rate_exc, cost_exc,
    device split {kWh, cost, rate} per device (via the account-type resolver),
    segments (+ reconciliation),
    band labels (derived from rate),
    cap state {charged_used, boundary_slot, boundary_frac, over}
```

Properties:

- **Deterministic & idempotent** — re-running on unchanged inputs is a no-op; safe to call
  anywhere, any number of times.
- **All-or-nothing** — it writes the *entire* derived set for the block, so a partial /
  stale combination is unrepresentable.
- **One path, every trigger.** Every one of these calls the same function and nothing else
  writes derived data:

  | Trigger | today | 4.4.0 |
  |---|---|---|
  | initial pricing | `_apply_pass2` | `reprice(block)` |
  | settlement re-rate | `_rerun_pass2_for_settled_block`, `run_deferred_verify_pricing` | `reprice(block)` |
  | late dispatch completion / reconcile | `reconcile_dispatch_overlay`, `_attribute_missing_ev_split` | `reprice(block)` |
  | gap-fill | `run_gap_fill_job` | `reprice(block)` |
  | API / CSV / HA import | `import_api_history`, `on_import_meter_update`, `repair_import_pricing` | `reprice(block)` |
  | tariff / VAT-calendar change | (ad-hoc) | `reprice(block)` |
  | historical backfill | `carbon` + `exc` + `iog_split` + `segment` (four passes) | **one** `reprice`-over-range |

The four separate historical backfills collapse into a single re-price-over-range. The
re-stamp / repair / back-attribution machinery **is deleted** — it existed only to patch
subsets after the fact, and there are no subsets any more.

> This is the invariant that would have prevented the VAT/exc, EV-split and segment
> staleness patches. It is the most important thing in this document.

## 5. Segmentation — uniform, device-labelled, reconciling

**Decided: keep segments, and segment *every* block uniformly** (not "only when needed").
This is settled, not a preference to revisit: segments are the only future-proof way to
price devices and remainders. Piling more columns onto the single block row to cover new
device/rate cases is what boxes us in — it multiplies code paths, makes each change ripple
through near-duplicate logic, and destroys any confidence in test coverage (the 4.3.x
pattern). One uniform representation is the model every code path conforms to (Principle 0).

The logical model — a block is an ordered list of priced portions, each tagged with an
**open device/attribution label** (`ev`, `battery`, `heat_pump`, `house`), summing to the
settled total — is exactly what future-proofs us (§8). Adding a device on its own rate
becomes "another segment with a new label," no schema change.

We considered denormalising the single-segment common case onto the block row for speed.
**Rejected**, on the device-tariff trajectory (§8): if blocks routinely carry
house + battery + heat-pump + EV portions, single-segment stops being the common case, so
the denormalised fast-path becomes the rare path plus a second shape plus a future
migration. One uniform representation is simultaneously the *simpler code* (one write path,
one accessor, no branch) and the *more future-proof schema*. The cost on today's trivial
blocks is a join, addressed by indexing on `(block_start, meter_id)` and the existing chart
cache — **not** by baking in a shape the device future invalidates.

- **Bands are labels, not facts.** A band is a name for a rate. It is computed from the
  rate at emit time and never stored as an independent column. (This directly killed the
  chart bug: live data only ever labelled blocks `off_peak`/`None` while the rate was
  correctly peak.)
- **Invariants enforced at write:** `Σ seg.kWh == settled kWh`, `Σ seg.kWh·rate ==
  settled cost`. A violation is a bug, asserted, not a silent drift.
- **The transition block** is just a block with more segments (EV off + EV peak + house);
  the settled cost reconciles it.
- **Migrated (legacy-column) segments carry the canonical tariff rate on a clean block.** The
  backfill (`segments_from_legacy`) reconstructs segments from the stored columns; on a clean
  block (`round(kWh×rate)==round(cost)`) it now carries the block's stored `imp_rate`/
  `imp_rate_exc` rather than back-computing `cost ÷ kWh`, which on a tiny-kWh block turned 6-dp
  cost rounding into 1/kWh rate scatter (a spurious ex-VAT tick on small billing bands). It falls
  back to `cost ÷ kWh` only for a genuinely settlement-adjusted block, where that is the only way
  to keep `Σ cost == settled cost`. The forward/seam path already carries the canonical rate.

`pricing_segments.py` (the pure core) and the `block_segments` table are **retained** —
they were never the problem. What changes is that they are fed only by the atomic re-price,
only from the account-type-selected source, with bands derived not stored.

## 6. Presentation read-contract — the chart is a dumb plotter

The re-price emits, **per half-hour for the whole day (including idle slots)**: the
applicable house rate, the applicable EV/per-device rate, and each device's kWh and cost.
Every surface reads that and only that.

- **Bars** plot stored per-device kWh. **Rate lines** plot stored per-device/house rates.
- Idle-slot rates come from the **tariff schedule** (a fact the pricing layer already
  knows), so the line is continuous without the chart inventing anything.
- The chart owns *how* it draws (step shape, colour, gap handling, hover, truncation) —
  never *what* the value is.
- If a line looks wrong, the fix is in the re-price/emit layer, **never** in the chart.

This retires the whole class of chart logic we churned on this session (band reading,
window/freebie reconstruction, hold-to-noon state machines). It also resolves the
`iog_cap_device_pricing_design.md` **Route 1 vs Route 2** question: that doc chose Route 2
(each surface re-derives) *because we had no capped multi-device DB to validate Route 1*.
We now have the 3h-cap Highgrove fixture (§10), so we take the disciplined **Route 1** —
compute once at the source, plot everywhere — which is what makes presentation dumb.

## 7. Migration (intrinsic to this design)

Because all derived data is a pure function of truth, migration is conceptually trivial and
is *the same operation as everyday re-pricing*:

1. Land the schema changes (namespace/separate derived columns; bands cease to be stored
   facts; segments uniform).
2. **Re-price every historical block** through the one function (a bounded, resumable
   sweep — the collapse of the four backfills). This rebuilds rate/exc/split/segments/bands
   from settled truth in one consistent pass.
3. Delete the re-stamp/repair/back-attribution code and the three now-redundant backfill
   passes.
4. Retain physical-device raw data untouched.

Guarantee: **non-IOG and IOG-uncapped are byte-identical after migration** (the house-band
rate equals `rate` there, the split is pure attribution, bands render the same). Only capped
IOG changes, and it changes *toward* the settled bill.

### 7a. Upgrade & migration ordering (the rule)

1. **Additive schema migration runs FIRST, then backfills fill it.** Columns must exist before
   anything writes them. `block_store` ensures/adds columns at connect; the backfills run as
   startup tasks after. Never backfill a column that doesn't exist.
2. **Prefer DEPRECATE-IN-PLACE over destructive drops.** Retiring a stored field (e.g. bands →
   derived-from-rate) means *stop reading it* and leave the column physically present. Never
   drop a column a backfill or reader still touches — that's the one ordering that can break a
   jump-user mid-upgrade. (Consistent with §3d keep-don't-prune.)
3. **Cross-backfill ordering: a backfill that DERIVES from another's output must wait for it.**
   The segment backfill builds segments from the split columns, so it now **defers until the
   IOG split backfill is done** — otherwise a dispatched block gets a permanent house-only
   segment (columns say split, segments say house-only; a run-order divergence between
   instances, and a plausible root of the original prod-vs-prod-dev mismatch). A single unified
   per-block sweep would remove this whole class (split + exc + segments in one pass).

### 7b. Capped newcomers — what history we can reconstruct

A user who installs EMT *already on the capped tariff* is a distinct case from an upgrade:

- **Inc billing (settled kWh + cost) is available for ALL history via the API**, so their
  totals are correct from day one.
- **The EV/Home split, the cap classification, and therefore the boundary/transition blocks all
  require the completed-dispatch signal**, and the API only serves completed dispatches for a
  bounded recent window (~90 days — confirm the exact bound). So:
  - *Within the dispatch window:* full split + cap bands + boundary blocks reconstructable.
  - *Older history:* grid-only at the settled (blended) rate — no EV/Home split, no cap bands,
    **no transition blocks**.
- So a capped newcomer **will not see transition blocks in charts older than the dispatch
  window** — expected, not a bug. The settled cost can't be back-solved into a split (one
  blended figure, two unknowns), so dispatch is the only source. Because we retain dispatch
  going forward (§3d), the full-split window **extends forward from install**, so the gap is
  bounded to the deep past and never grows.

## 8. Why extensible now — the device-tariff trajectory (evidence)

Market-wide half-hourly settlement (MHHS) is mid-rollout: supply points began migrating
Sept 2025, ~50% of meters were across by early Aug 2026, and effectively all customers are
due to be half-hourly settled by ~Oct 2026. Once every customer is settled half-hourly, a
supplier is *directly* rewarded for shifting load, so time-varying and **device-shaped**
tariffs become structural, not optional; commentary around the rollout explicitly expects a
"second wave" of smart heat-pump tariffs. The device-control model already exists — IOG is
"hand us the charger for a cheaper rate," Cosy is the heat-pump analogue, Flux was the
solar-battery one. Honest nuance: today it is mostly time-of-use *windows* plus active
*control* for EVs; per-device dispatch-priced heat-pump/battery tariffs are emerging, not
yet mainstream — but the settlement change is the wind at their back. (Sources listed at
the end.)

Consequence for the schema: **open device labels + a per-device attribution resolver +
uniform segments** are the cheap insurance that a battery or heat-pump tariff is an
*additive* change, not another rewrite. That is the "don't box ourselves in" the earlier
EMT versions failed at.

## 10. Phasing

Phase 1 is the design-confirming, first-testable slice; billing charts are your only visible
way to spot issues, so they are in Phase 1.

> **Correction (post-visual-validation):** Δ1–Δ3 shipped under a *re-derive* framing —
> `reprice_block` recomputes the off-peak/peak classification, and the fixture re-priced every
> dispatched block through it. Per §3b that is wrong: `reprice` must **inherit** the finalised
> eligibility and only layer the cap split. Corrective deltas: (Δ1′) `reprice_block` takes the
> finalised base rate / eligibility as an input and only flips over-cap *smart* charging to
> peak; (Δ2′) the fixture preserves each block's finalised rate, keys smart-vs-bump on
> `imp_rate_ev`, accumulates smart charged-time only, and flips over-cap smart segments to
> peak — leaving bump/day blocks untouched; (Δ3′) `chart_emit` house line reads the
> house-attributed **segment** rate, not the block blend. The confidence flag already exists
> (`needs_review`/`review_reason` via `_reconcile_decision`, §3b) — `reprice` consumes it. The
> durable eligibility **stamp** is the one genuinely new Phase-2 item.

- **Phase 1 — core + billing charts (design confirmation).**
  The atomic `reprice(block)`; the account-type EV resolver (EV only); uniform segments fed
  by it; bands derived; the emit contract; day chart + side panel + billing summary reading
  the emitted values as a dumb plotter. Validated on the **3h-cap Highgrove UC** (§ below)
  and byte-identity on uncapped/non-IOG. **Exit criterion:** the capped Highgrove day
  renders correctly with zero chart-side rule logic, and reconciliation holds every block.
- **Phase 2 — write triggers unified.** Route settlement, reconcile, gap-fill through the
  one re-price; delete re-stamp/repair/back-attribution; collapse the backfills into one
  re-price sweep; the migration.
- **Phase 3 — import & HA surfaces.** API/CSV import, historical-import wizard, HA sensor
  backfill / decommission / un-retire, delete-range, all driving `reprice`.
- **Phase 4 — live card & remaining presentation.** Provisional-off-peak card, cap
  indicator, Usage Stats/Insights, the physical-vs-synthetic coverage decision.

Each phase keeps the reconciliation invariant and the uncapped/non-IOG byte-identity as
standing acceptance tests.

### 10a. Phase 3 — grounded surface inventory & sequence (scoping)

The forward path (finalise / settlement / reconcile) is unified on `_reprice_main_import_block`
(Phase 2). Phase 3 is the surfaces that still write/mutate blocks **outside** it:

| # | Surface | Today | Routing needed |
|---|---|---|---|
| 1 | **Bulk API import** (`import_api_history` / `run_api_import_job`) | writes **only rate + cost** via `block_store.reprice_imported_block`; split/exc/segments/carbon come from the **four historical backfills** | the primary target — see the (A)/(B) fork below |
| 2 | **Repair pricing** (`repair_import_pricing`, reprice-queue drain, deferred verify) | re-prices rate/cost via `reprice_imported_block`; same backfill dependency | same as import |
| 3 | **CSV import** (`reprice_imported_blocks_from_csv`) | older history; same rate/cost-only pattern | onto the chosen import path |
| 4 | **Gap-fill** (`run_gap_fill_job` / `build_gap_blocks`) | **P3.2: provisional pricing does NOT conform** — prices inline from `last_known_rates`; derived fields via the import-style finish. **Conforms once settled** (settlement → one re-price) | fold the provisional pricing into (A) with import; settled path already conforms |
| 5 | **Delete-range / meter-delete** | `delete_blocks_for_date_range` cleaned `reads`+`generation_mix` (block_id) but **not `block_segments`** (keyed by block_start, no FK) → **orphaned segments** | **P3.1 (done)** — all four delete paths now clean `block_segments` |
| 6 | **Live HA-sensor import** (`on_import_meter_update`) | **P3.2: CONFORMS** — `finalise_block` → `_reprice_main_import_block` | none (verified) |

**The central fork (import unification):**
- **(A) Route import/repair/CSV through `_reprice_main_import_block`** so each imported block gets
  split/exc/segments/carbon atomically — which **collapses the four backfills**. This is the Δ4d
  idea parked in Phase 2; it was low-value *there* because the forward-path backfills are no-ops,
  but on the **import** path they are **load-bearing**, so this is where the collapse pays off.
  Higher value (one model), higher risk, perf-sensitive (a re-price per block over years).
- **(B) Keep the backfills, prove they conform** to the one re-price. Safer; two pricing models persist.

**Sequence:** **P3.1** delete cleans `block_segments` (done — restores the Σ segments == grid
invariant, de-risking the rest). **P3.2** confirm live-sensor + gap-fill already conform.
**P3.3 — decided: (A), to remain faithful to the one model.** Route bulk import + repair + CSV +
gap-fill-provisional through `_reprice_main_import_block`, then retire the four backfills once the
routed path is proven byte-equivalent to them (staged: route first, prove conformance, collapse
last). Perf-guarded (re-price per block over years — batch/pace like the import loop). **P3.4** CSV
+ gap-fill provisional onto the same path.

**Conformance gate — corrected (P3.3a).** The three backfills use *legacy* per-aspect
derivations (`_exc_rate_for_block`; `pricing_segments.segments_from_legacy`); the forward seam
uses seam segments + exc off the POST-split rate. So routing history through the seam is **NOT
byte-identical to the three backfills** — it is byte-identical on **uncapped / non-IOG** (the
standing guard: no split; exc = inc×ratio; the same single-house legacy segment) and on
**capped / dispatched** blocks it **realigns history to the forward model** (full-fidelity seam
segments, post-split exc) — intentionally superseding the lossy legacy derivation. The gate is
therefore *"uncapped byte-identical + capped conforms-to-forward (invariants hold)"*, which is
exactly what "remain faithful to one model" means. P3.3b flips the sweep in as primary (backfills as net); P3.3d gives it a forced self-heal so
it covers new import / gap-fill / CSV blocks; P3.3c widens the sweep to the exc superset and retires (unschedules) the three legacy backfills — the sweep is the sole historical derivation; the backfills stay dormant for a release, then delete.

### The test UC — 3h-cap Highgrove

Real Highgrove dispatch never exceeds the 6-hour cap, so we keep re-pricing the real DB
under a **3-hour** cap to force genuine over-cap days, a boundary block and a blend — a real,
testable capped account from real bulk + real dispatch. **Decided: regenerate the fixture
under the new model** — the user supplies a fresh real DB at the start of Phase 1, and we
rebuild the 3h-cap fixture through `reprice` so it is authoritative *by construction*
(settled-anchored, synthetic-EV-only, clipped+unclipped energies, bands derived) rather than
carrying the old assumptions (the current one bakes in a since-corrected fake EV-peak rate
and stored bands). This is the Phase-1 opening task.

### Guardrails / CI

- Assert `Σ seg.kWh == settled kWh` and `Σ seg.cost == settled cost` at write time.
- A verify-pricing sweep that re-derives a sample and flags any drift (reuse the existing
  `verify_pricing` cursor).
- A test asserting **every** trigger routes through `reprice` and leaves no derived field
  behind — the staleness class becomes a test failure, not a production patch.

## 11. Unresolved — needs investigation (not blocking Phase 1, but 4.4.0 must resolve)

1. **Carbon — resolved (§3a), core shipped (Δ5):** carbon stays a **separate derived axis**
   (kWh × CO₂ intensity; price never enters). The credit is the **draw gap** unclipped −
   clipped valued at the current grid intensity — NOT an export/generation offset. It shares
   the energy substrate reprice already emits (clipped billing EV + unclipped carbon EV +
   house grid kWh). 4.4.0 re-sources the EV from the synthetic dispatch device (single-source
   rule, as cost). Open sub-point **decided: adjacent pass** — the CO₂ number lives in
   `carbon.py`, keyed on the emitted energies, so the price core stays carbon-free by
   construction. Δ5 = pure core + tests; engine wiring is the next delta.
2. **Physical-vs-synthetic coverage gate — RESOLVED (P4.5).** `_day_segment_split` prices EV
   cost/rate from the dispatch segments (synthetic, single-source) while the EV BAR keeps the
   physical charger's metered grid-kWh shape; the house remainder absorbs the metered-vs-dispatch
   residual (Σ device == grid). `_dispatch_ev_slot_map`'s coverage gate keeps the physical device
   until it decommissions, then the synthetic takes over. Decision made: cost=dispatch, bar=physical.
3. **Per-device resolver for battery / heat-pump** — build the shape now, implement only EV;
   revisit when a real device tariff (and its control signal) exists.
4. **Non-IOG-EV fallback** — does the physical-device path need its own thin split path or
   does it ride `reprice` with `dispatch = ∅`? Lean: the latter.
5. **Provisional vs settled** — enumerate exactly which fields freeze at settlement (cost,
   kWh) and which stay derived (the split can still move on a late completion), so a
   post-settlement split change is never mistaken for a billing error.
